## What this session found and fixed

### 1. The ONL hostname was a race, not a one-off

Exaware's bring-up matches the ONL shell by the literal `"@localhost"`
(`CmpCliSession.java:69`). Something rewrites `/etc/hostname` back to `router`
about three minutes after boot (file mtime 17:56 on a box booted 17:53), so
setting the hostname once before a run is a race, and on 2026-09-09 the run
lost it, which is why the previous TC02 attempt died at
`Failed to enter specific session mode. Wanted mode: ONL`.

`scripts/lab/onlctl.py pin` now runs a watchdog on the ONL host that
re-asserts `hostname localhost` every 5 s for the whole run, and truncates
`/var/log/syslog` at the same time. `cycle.sh` calls it instead of the old
set-once-and-verify loop. TC02 has cleared the ONL transition on every attempt
since.

This remains **Exaware's bug to fix properly**: the image should set the ONL
hostname, or the regex should stop assuming it. Any suite fails on that image,
not just this one.

### 2. The traffic statistics view never existed

TC02 failed every traffic assertion with

```
Fail: No results where:  TRAFFIC_ITEM: TI_AC1_TO_AC2
error in state view name, fail to find view.
::ixNet::ERROR-7008-Could not apply traffic,Error in L2/L3 Traffic Apply
```

while the traffic was running perfectly. The ERROR-7008 was a red herring: the
apply succeeds, and ixia_lib's own `trafficApply` throws on its **last line**,
which reads the page of a statistics view that does not exist.

IxNetwork only builds the "Traffic Item Statistics" view for items that carry
tracking. Ours carried none (`trackBy=''`), and the `.ixncfg` we ship was
saved from a session that never set it. TC01 never noticed because it is the
one test that reads no traffic statistics.

Fixed by tracking every item by traffic item before `generate`, in both
emitter branches and in `EVPN_traffic.tcl`. Device-verified on chassis
10.1.70.108, same rig, same `.ixncfg`:

```
VIEW (before fix): ABSENT
VIEW (after apply): isReady=true

TI_AC1_TO_AC2  Tx 9983  Rx 19966   <- flooded to BOTH ACs, which is FLOW-030
TI_AC2_TO_AC1  Tx 9983  Rx  9983   Loss 0
TI_AC3_TO_AC1  Tx 9983  Rx  9983   Loss 0
```

Full account: `deliverables/M2/evidence_traffic_item_tracking.txt`.
Locked by `tests/test_codegen.py::test_traffic_items_are_tracked_before_generate`
(proved to fail with the fix removed) and ratcheted as capability
`traffic.statistics_view`, which now refuses both the 2026-08-14 and the
2026-08-24 packages.

### 3. What running TC02 then found

The plumbing fixed, the numbers arrived, and they said the expectations were
wrong. Four more defects, all fixed and locked by tests:

| | |
|---|---|
| Every traffic step asserted "all three items running" | the emitter computed `step.expect_key` and discarded it. At most steps exactly one item is unsuspended |
| Expected Rx assumed Rx = Tx | AC2 and AC3 share a vport and the frames are broadcast, so a flooded frame is counted twice: `TI_AC1_TO_AC2` is Tx 1000 / **Rx 2000**. That 2x is the flooding assertion, and it is derived from the profile |
| `RowDataTable` declared after `SuiteTableParams` | the table freezes the rows present at construction and Java runs initialisers in order, so later rows indexed past the end: `ArrayIndexOutOfBoundsException: 6 >= 6` |
| TC03 aged out MACs it had never learnt | its prep starts every item suspended, so all three of its assertions were trivially true on an empty MAC table. It now learns first |

And two about captured expectations, which only appeared once captures existed:

- **Absence expectations carried table furniture.** Column headers print
  whether or not a row remains, so "verify the MACs aged out" demanded that
  `MAC ADDRESS` disappear. `fake_pass.is_structural` existed for this and was
  never called by the emitter.
- **A capture of an unscoped command is a snapshot of one moment.**
  `show bgp l2vpn evpn table evi detail` prints every route, so three steps got
  byte-identical expectations. FLOW-030.S05 ("AC1's MACs advertised") froze
  AC2's route too and failed on a correct device with
  `Missing lines: [Type=2: VLAN-ID=0, MAC=00:00:02:00:00:01]`. Steps now carry
  an `expect_subject`.

What the rig cannot prove is now stated rather than claimed: a broadcast cannot
stop being flooded, and a MAC move between two circuits on one vport is
invisible to a per-port counter. Egress tracking by VLAN was tried and refused
by the chassis. The move is asserted on the DUT, by FLOW-030.S15 and S16.

`cycle.sh` reboots the DUT, waits for it to settle, pins the ONL hostname,

because of the device facts below.

## Device facts every run has to work around

**1. Deleting an EVI aborts bgpd.** `assert (_Bool)(ipi_evi_p)`,
`bgp_evi.c:310`, `bgp_evi_delete`. The service then survives in operational
state after leaving the configuration:

```
no l2-services evpn evi-1 ; commit  ->  Commit complete.
show configuration l2-services      ->  % No entries found.   (gone)
show evpn summary                   ->  EVPN NAME: evi-1      (still there)
```

Only a reboot clears it, so only the first test after a reboot can start from
the state it asserts. This is why the tests cannot run back to back.

**2. The ONL hostname.** See above. Handled by `onlctl.py pin`.

**3. Their syslog check pages.** Bring-up runs
`less /var/log/syslog | grep ... -c` on the serial TTY. Once the syslog is
more than a screen, `less` waits for a keypress and the command times out at
100 s. `onlctl.py pin` truncates it.
