2. THE COUNT DROPPED FROM 7 TO 2, AND THAT IS THE POINT
--------------------------------------------------------------------------------
The first capture run on this DUT reported 7 usable expectations, the same as
the previous milestone. Five of them were worthless, and `capture` was the thing
that should have caught it. Here is one, in full, exactly as recorded:

    FLOW030_S04_AC1_MACS_LEARNT_LINES   (status: ok)
    show evpn mac-address-table name evi-1 source agg-eth-1.100
        'LOC:  L - local, R - remote'
        'L-FL: D - dynamic, S - static'
        'R-FL: N -learnt, U - Unlearnt'
        'ACT:  S - Single-Active, A - All-Active'
        'EVPN Name: evi-1, Service Model: vlan-based, Local Label: 40960'

That is the table's legend and header. There is not a single MAC address in it.
The step it belongs to is called "Verify AC1 source MACs are learnt". An
assertion built from those lines passes whenever the device prints its legend —
which is always, on a working device and a broken one alike. It could never
fail, so it could never detect a regression.

`capture` already refused to record a rejection or an explicit "no entries
found" as an expectation. It now also refuses a MAC table that contains no MAC
address, and says why:

    the MAC table printed its legend but no MAC addresses - nothing has been
    learnt yet, so there is no expectation here that could ever fail

Nine steps now report a warning instead of a false assertion. The suite asserts
less and means more.


3. WHY THE MAC TABLES ARE EMPTY
--------------------------------------------------------------------------------
Not a device problem and not a command problem — there is no traffic. EVPN
learns from SOURCE MACs, and `ixia_lib.tcl` exposes
`editTrafficRawDestMacAddr` with no source equivalent. Until there is a
src-MAC proc or an .ixncfg carrying the three traffic items, nothing is offered
for the DUT to learn, so the MAC-table and Type-2 rows have nothing to show.

The four `show bgp l2vpn evpn table evi detail` rows are empty for the matching
reason on the control plane: no BGP EVPN peer is wired to this DUT, so no
Type-2 or Type-3 route is originated or received.

Both are recorded as EMPTY — "needs state" — rather than UNSUPPORTED, because
the distinction matters: UNSUPPORTED sends someone to fix a command that is
already correct.


4. WHAT THE TWO USABLE CAPTURES ARE WORTH
--------------------------------------------------------------------------------
`show evpn detail` and `show evpn broadcast-domains name evi-1` return real,
state-dependent content on a configured EVI — the service type, the route
targets, the aging time, the MAC limit, and the three bound interfaces. They
would change if the service were misconfigured, so they can fail, so they are
worth asserting.

Real defaults read off this build, for the record:

    MAC Limit         65520           (range <1-250000>; 250000 is the
                                       configurable maximum, not the default)
    Advertise MAC     Enabled
    ES DF Waiting     3 seconds
