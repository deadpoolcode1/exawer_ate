4. EVPN BEHAVIOUR DEMONSTRATED
-------------------------------
MAC learning on the DUT, from real IXIA traffic:

    VLAN  MAC ADDRESS        LOC  SOURCE
    ---------------------------------------------
          00:00:01:00:00:01  L    x-eth0/0/8.3380
          00:00:02:00:00:01  L    x-eth0/0/18.3380

Local MAC move — AC2 and AC3 deliberately source the same MAC, so shifting
traffic from AC2 to AC3 is a purely local move:

    before   00:00:02:00:00:01  L  x-eth0/0/18.3380     (traffic on AC2)
    after    00:00:02:00:00:01  L  x-eth0/0/26.3380     (traffic on AC3)

Aging — with that traffic stopped, the entry leaves the table, which is what
TC03's absence assertion checks.


5. FIVE DEFECTS THIS RUN CLOSED
--------------------------------
Each of these previously presented as success: the config committed, the
`show` output looked right, and every call returned without error.

(a) SOURCE MAC — settable all along.
    The field is `ethernet.header.sourceAddress-2`, not `-1`. The suffix is
    the field's POSITION in the ethernet stack, read off the chassis:
        field:"...destinationAddress-1"  ->  'Destination MAC Address'
        field:"...sourceAddress-2"       ->  'Source MAC Address'
    This dissolves the previously reported dependency on a source-MAC proc in
    ixia_lib.tcl. No change to Exaware's infrastructure file is required.

(b) AC SUB-INTERFACES NEED `vlan-id`.
        interface x-eth 0/0/18.3380
         l2-transport enable            <- admin-up, bound, and inert
    The port counted 219,000 frames received while the sub-interface counted
    0, and `show evpn detail` still listed it as a bound attachment circuit.
    The sub-interface NUMBER does not select the VLAN; VPLS_N1.cfg pairs
    `int2.1` with `vlan-id 2` the same way.

(c) RAW TRAFFIC ITEMS WERE UNTAGGED.
    A raw item's frame is its protocol stack, and that stack was
    ethernet + fcs. Tagging the vport's interface governs protocol emulation,
    not raw frame content, so every frame arrived untagged and matched no
    vlan-id sub-interface.

(d) ENABLING A TRAFFIC ITEM IS NOT TRANSMITTING.
    `trafficItem -enabled true` plus `trafficApply` leaves the chassis
    configured and silent. An explicit start is required, and the state is now
    read back before any assertion depends on frames having moved.

(e) ABSENCE STEPS WERE ASSERTING PRESENCE.
    "MACs aged out", "Type-2 withdrawn" and "MAC table starts empty" are
    claims about something being GONE. Capture records state while it EXISTS
    and refuses empty output, so each of those steps had been filled with
    exactly the rows that ought to disappear. They now assert absence, scoped
    to the circuit whose traffic stopped rather than to the whole table.

7. KNOWN LIMITS, STATED PLAINLY
--------------------------------
  * No Type-2/Type-3 ROUTE EXCHANGE has been demonstrated. IXIA cannot
    emulate a BGP EVPN speaker on this chassis: starting one fails with
    "ERROR-1005 ... There is no license available for BGP EVPN". Isolated to
    that feature — the same neighbour starts and establishes with plain
    ipv4-unicast. Per Exaware, the current TCs do not need it.
  * The three attachment circuits and the L3 core link cannot coexist:
    pc-3080 has exactly three DUT<->IXIA links, so a profile with a core has
    two ACs and cannot run FLOW-030's MAC move. `ate codegen` reports the
    flow as not generated rather than emitting fewer tests silently.
  * 5 of 11 expectations on the 2ac-core profile remain empty, all of them
    BGP-table reads, for the licence reason above.
